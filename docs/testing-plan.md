# Software testing plan

Version 0.1, 2026-09-20.

This document specifies how LCA is tested: what test-driven development means for this project specifically, the taxonomy of test types and what each covers, the fake-provider strategy that makes the agent loop testable without a real model, and a dedicated treatment of cache-behavior testing, since keeping a provider's prompt cache warm is close to a functional requirement for a coding agent, not a performance nicety. It is a companion to the software requirements and design document, not a restatement of it; requirement identifiers referenced here are defined there.

## 1. Why test-driven development, specifically here

The usual case for TDD is a human one: writing the test first clarifies the requirement before the implementer commits to an approach, and the resulting suite catches regressions a human would otherwise reintroduce by forgetting an old constraint. Both apply here. A third reason applies more sharply than usual, because of who is expected to write most of this code.

An AI agent implementing a feature in a fresh session has no memory of the design discussion that produced the requirement, no tacit sense of "we tried that and it broke something," and no discomfort about producing code that looks plausible but is subtly wrong in a way a human reviewer would catch on sight. A failing test is a piece of ground truth that doesn't depend on the implementer's judgment agreeing with the reviewer's. Red, green, refactor is not a style preference in this context; it's the mechanism by which a requirement survives being handed to an implementer with no memory of why it exists.

This has a direct consequence for how tests get written: a test should be traceable to a requirement identifier, an ADR, or a defect identifier, not written free-form against the author's own understanding of what the code should do. Section 11 specifies the mechanism that keeps this traceable rather than aspirational.

## What a failing test means

Failing tests come in two kinds, and confusing them is how a test suite
becomes friction instead of a safety net.

**Expected failures** are part of building something new. A new
requirement, a new specification, a whole new behavior legitimately
leaves red behind for a while: the new guard is written first and stays
red until the implementation lands (the red-green discipline above), and
an existing test that pinned the behavior being deliberately replaced
must change with it — updated or retired in the same change, named by
the brief or the decision that sanctioned the change. A test that pins
an implementation detail rather than an observable contract is a test
waiting to become this kind of failure; write tests against behavior so
that redesigning the code underneath does not break them.

**Unexpected failures** are the real signal. If a change to one
component breaks a test in another, something is wrong — an
architectural boundary is leaking, or the change did something its
author did not intend. That is a stop-and-investigate moment, not a
loosened assertion. The rule of thumb: a red is acceptable exactly when
the change was *meant* to make it red. Everything else gets root-caused
before work continues.

## 2. Test taxonomy

Ten categories. Each has a home in the crate layout, a tool, and a place in the CI pipeline described in section 13.

**Unit tests** verify one function or one small module in isolation and run in milliseconds. They live beside the code they test in the same file under `#[cfg(test)]` when they test non-public internals, and in per-crate `tests/` binaries when the behavior is reachable through the crate's public API; both placements are unit tests in this plan. Every crate with behavior has them; there is no crate where unit tests are optional.

**Integration tests** verify a flow that crosses module or crate boundaries within a single process, live under each crate's `tests/` directory, and use `lca-testkit`'s harness and fake provider rather than a real model or real network access. The six flows diagrammed in `docs/flows.md` are the primary integration test targets: a turn with a tool call, context assembly with compaction and transform, extension instantiation and capability resolution, the OAuth loopback flow, the streaming pipeline, and cancellation reaching a running extension call.

**Conformance tests** verify the extension ABI itself, not any particular extension. The conformance extension under `extensions/conformance/` exports and imports every surface defined in every WIT world and every host capability, and is run in both native-linked and WASM mode with an assertion that the two produce identical results, per FR-EXT-6. It is also built against the previous ABI minor version and loaded by the current host, verifying the support window in NFR-19 actually holds rather than being an assumption nobody checks.

**Regression tests** exist because a defect that reached a release and got fixed should never come back silently. Each one is named after the defect's tracking identifier, following pi's convention of naming regression test files directly after the issue number they close, and lives under `tests/regressions/`. NFR-24 already requires one per released defect; this document specifies the naming and location. The file is written in the same change as its fix, and it is the permanent named guard even where the fix also carries tests elsewhere in the suite.

**Property-based tests**, using `proptest`, verify an invariant across a generated range of inputs rather than one hand-picked example. This project has several state-machine-shaped invariants well suited to it: session log round-tripping, compaction never dropping a record outside its replaced range, the context-transform chain preserving message order except where a transform explicitly changes it, and the permission store's proposal-hash comparison detecting any single-byte change to the approved set.

**Fuzz targets** verify that a parser handling attacker-influenced input never panics or produces undefined behavior, following the threat model's own list: the manifest parser, the session log reader, the HTTPS-archive resolver, the canonical ABI decode path, the provider SSE/event-accumulation stream (FR-PROV-7/8), and the headless `--json` envelope serializer.

**Snapshot tests** verify that a piece of generated output, a rendered terminal frame or an assembled request, matches a reviewed golden file, so a change to either shows up as a diff a human approves rather than as a passing test that silently started asserting something different. Section 10 covers the specific and unusual use of this technique for catching cache-breaking regressions.

**Performance and benchmark tests** verify the numeric NFRs. Binary size,
interpreter-host size, cold start, idle memory, the interpreter build's
no-compiler property, and the cache-hit ratio are measured by
`scripts/perf-gate.sh` in the pipeline's size-and-startup gate, and a
threshold breach fails the build the same way a failing test does. The
remaining numeric budgets are asserted as ordinary tests with a `// Verifies:`
marker (instantiation time, hook-call overhead at 1 ms, cancellation latency),
so each threshold lives in exactly one place. There is no `criterion` harness;
the gate script and those tests are the measurement.

**End-to-end tests** drive the actual `lca` binary as a subprocess, exercising the real CLI and the real filesystem, still against the fake provider rather than a real model. Rendering is exercised two ways: through the project's own line-string renderer against a fake terminal in unit and integration tests, and on real terminals by the tenth category below. These are the slowest and fewest tests in the suite and exist specifically to catch the class of defect that only shows up when every layer is real except the model.

**Real-terminal tests** drive the agent inside an actual terminal emulator and assert what is on screen. They exist because virtual-buffer rendering cannot see the terminal-shaped failure class: a secret that leaks into the visible frame, a resize that leaves a stale row, a control sequence from hostile content that corrupts the display. Unix runs them under tmux; Windows runs them under a pseudo-console (ConPTY). The checklist is identical across both harnesses: startup renders, a scripted turn streams and renders, the permission modal works, the secret prompt masks its input, resize re-renders, a clean quit writes `session-end`. A platform without its harness skips these tests and never fails them. Section 14 has the details.

## 3. The fake provider

`lca-testkit`'s fake provider is the single most load-bearing piece of test infrastructure in the project, modeled directly on pi's `providers/faux.ts`: a provider implementation that speaks the real `provider` world ABI and returns scripted content in a defined order, so every test exercising the agent loop, compaction, retries, cancellation, or tool dispatch runs deterministically, at zero cost, with no network access, through the actual dispatch path rather than a shortcut around it.

A test scripts a fake turn as an ordered sequence of events matching the typed provider stream from ADR-0004: text deltas, reasoning deltas, a tool call's start, argument deltas, and end, a usage event, or an error, in whatever order the scenario calls for. The harness exposes a small builder so a common case, "the model replies with this text and calls this tool with these arguments," is a few lines, not a hand-assembled event stream.

```rust
let fake = FakeProvider::builder()
    .turn(|t| t
        .tool_call("read", r#"{"path":"notes.md"}"#)
        .usage(Usage { input: 1200, output: 40, cache_read: 0, cache_write: 1200, ..Default::default() }))
    .turn(|t| t
        .text("The file contains three notes.")
        .usage(Usage { input: 1240, output: 12, cache_read: 1200, cache_write: 0, ..Default::default() }))
    .build();
```

Every fake turn carries a usage record, including cache read and write counts, per ADR-0017. This is deliberate and non-optional in the builder: a test that doesn't care about cache behavior can leave the fields at zero, but a test that scripts a realistic multi-turn conversation without cache numbers is scripting something that couldn't happen against a real caching provider, and section 9 depends on being able to script exactly this.

The fake provider also simulates a capability-denied path, an error mid-stream, and a stream that ends with a tool call still open, since these are the failure paths FR-PROV-8 and the accumulator tests need and a real provider will not reliably reproduce on demand.

## 4. The harness convention

Following pi's own `test/suite/` convention directly: integration tests use a shared harness, never call a real provider, a real API key, or the network, and stay deterministic enough to run in CI without flakiness. The rule, adapted from pi's own stated policy: use the fake provider, do not extend a legacy ad hoc setup path once the harness covers the need, and if a test genuinely cannot be expressed against the fake provider, that is a signal the harness is missing a capability, not a reason to reach for a real one.

Real-provider tests do exist, one per first-party provider extension under `docs/providers/`, and are gated behind an environment variable naming the credential they need, skipped rather than failed when it is absent, matching pi's own pattern of never blocking a contributor's local run or the default CI job on a credential they don't have.

**A real-pty row waits for the marker, not for a byte count** (gh #535). `pty_spawn_delivers_program_output_and_exit_code` used to loop `pty.read` until `out.len() >= 64` or a 5 s deadline — a *sampling* exit condition, where a first read that returns a partial line satisfies the length without containing the marker, and a slow runner can spend the whole deadline. Neither is a property of the product, so the row measured the machine. It now reads until the marker arrives or the session closes, and its failure message distinguishes the two: a pty that **closed** without the marker is a product answer, a **deadline** that expired is a runner one. That distinction is the whole reason the row sat ambiguous for two cycles, so it is printed rather than left implicit.

The same cycle found the sharper case, and it is the one worth remembering: `pty_spawn_delivers_terminal_output` is *not* sampling — the conformance guest loops until the host answers end-of-stream — so its `exit 0` with empty output was the **host** declaring a session drained before the child's tail was readable. A row that looks like a timing flake can be reporting a product defect through a truthful message; reading what the row actually does, before choosing a mechanism, is what tells them apart.

**A fake must model every ending its contract allows, not just the one the first test needed** (gh #351). `webfetch`'s canned network returned `Some(body)` on every read and never `Ok(None)`, and re-delivered the same bytes each call — so every row in that file exited through the 1 MiB input cap, the truncation branch, and the *successful complete fetch* path had never once run under test. Worse, because the loop kept appending, a small document grew until it hit the output bound, so a row asserting only "the page's text is present" passed identically under both endings. The rule that came out of it: when a harness answers a call that has an end-of-stream answer, the fake carries a cursor and returns the end-of-stream answer at the end. And the row asserts **which branch ran** — the read count, `ceil(len/chunk) + 1`, which no other ending produces — not only the bytes, because an output-only assertion cannot tell a complete read from a truncated one.

## 5. Test environment sandboxing

Every test that touches the filesystem or environment runs inside an isolated temporary `HOME` and config directory, constructed fresh per test, with no access to the developer's real credentials, git config, or shell environment. This follows the sandboxing pi's own `test.sh` performs before running its suite: an isolated `HOME`, an isolated package cache, a stripped environment, and `GIT_ASKPASS` disabled so nothing can prompt for real credentials by accident. `lca-testkit` provides this as a fixture every integration and end-to-end test gets by default, not as something each test author has to remember to set up.

## 6. Conformance testing in depth

The conformance extension is not a toy; it is the thing that makes the promise "native-linked and WASM are interchangeable delivery modes" a tested fact rather than an assertion in a document. It needs a case for every world, every host import, and every capability's denied path, not just the happy path:

Every world's every exported function, called once with valid input and asserted against an expected result. Every host import's granted path and its denied path, including the specific denial shapes that differ by capability: `credentials.get` returning empty rather than an error, `net` refusing a rebinding attempt distinctly from an ordinary denial, `fs` refusing a path that escapes its scope through a symlink created after the grant. The `pty` and `completion` capabilities' full grant-and-deny cycle, since these are the newest and least battle-tested parts of the catalog. The `compaction` and `context-transform` worlds' rejection paths, and the boundary-narrowing behavior from ADR-0017 when a transform touches the stable region.

This runs in native-linked mode and WASM mode on every pipeline run, with the two results diffed; any divergence is a defect regardless of which mode is "wrong," since the entire point of the dual-mode design is that there shouldn't be a wrong one.

**Keeping the committed fixture current (gh #427, gh #591).** The offline value above is served by one committed component, `extensions/conformance/fixtures/tool-world.wasm`, byte-identical to a fresh `cargo build -p conformance --target wasm32-wasip2 --release` and `include_bytes!`-ed by eighteen test files. It went stale once: the package had no refresh step anywhere — `scripts/wasm-check.sh` builds but deliberately refreshes nothing, and the publish workflow's fixture-refresh step names five other extensions — so when the hook worlds landed in `wit/` and the source, only this file's byte-identical twin (`component.wasm`, added by the 0.5.0 release commit and referenced by nothing, ever) and then the fixture itself drifted out of sync until a user hit `no exported instance named 'lca:ext/hook-message-end@0.6.0'`. Three guards now cover the failure, one owner per shape: `wasm-check.sh` compares **every** committed component (`extensions/*/fixtures/*.wasm`, derived rather than listed) against a fresh build of its own crate on every push, by **interface** — `wasm-tools component wit` on both sides, never the bytes (the profile is `lto = "fat"`, `codegen-units = 1`, so a hosted runner produces a different file for the same component and a gate that reddens on codegen noise is worse than none; gh #591 widened this from one hard-coded path after two fixtures, `codex` and `grok`, had gone stale behind it, and it prints each component it checks and skips an unbuilt directory with its reason rather than passing quietly). Refresh stays a deliberate reviewed step — refresh stays a deliberate reviewed step: `cp target/wasm32-wasip2/release/conformance.wasm extensions/conformance/fixtures/tool-world.wasm`); `crates/lca-ext-host/tests/fixture_current.rs` walks the fixtures directory at run time and loads every file through `ExtHost::load`, which links every world the manifest declares, so a stale fixture and a second stale file both fail by name; and `tests/regressions/427-*.rs` pins that no committed fixture may sit without a test file referencing it (the unconsumed-twin mechanism that hid this one for two weeks) plus the load again at the repo gate. Residual, named: the byte comparison assumes a deterministic release build — verified across full rebuilds today — so a toolchain bump that changes bytes would fail the gate on an unmodified tree, loudly, with the one-line refresh in the message rather than letting staleness return silently.

## 7. Regression test policy in depth

A defect that reaches a released build gets a test that reproduces the minimal case, named after the issue that tracks it, and placed under `tests/regressions/`, following pi's own directory of numbered regression files directly. The file name carries the issue identifier and a short description, for example `1842-compaction-drops-tool-result.rs`, so the file itself documents which bug it guards against without needing to open it. When a defect has no issue number — a finding in a review report, for instance — the report's finding number is the identifier. A fix for a defect that reached any release ships with its regression file in the same change; an ordinary-suite test may exist alongside it, but the named file is the guard that survives refactors.

**The module walk serves any crate** (gh #543). Gh #574's lesson was paid in `lca-ui`; gh #543 paid it again in `lca-cli`, where 17 regression rows read one of the four files that cycle moved. `crate::module_sources`/`module_text`/`text_of` therefore carry no crate name: the walk is ordinary `mod` syntax, so `crates/lca-cli/src/tui/mod.rs` and `crates/lca-ui/src/chat.rs` are the same call. Two caveats that came out of the second crate. A row whose subject is **one file's** property (an absence, like "`/reload` has no sweep of its own") must keep reading that file - a module walk would let a third sibling hide the thing it forbids. And a helper module for an integration test belongs under `tests/common/`, never at `tests/`' top level, because cargo builds every top-level `.rs` there as its own test binary (gh #543's first `e2e_terminal` split failed to compile exactly that way).

**A structural guard reads the module, not one file of it** (gh #574). Guards that grep a source file are the ones that survive refactors *and*, as this cycle found, the ones a refactor can silently disarm. Nine `lca-ui` files were split along their own seams; six guard rows went red because they keyed on a **filename** - `chat.rs` for the key-map setter, `transcript/mod.rs` for the replay arms, `chat_keys.rs` for the picker arms - and the arm they looked for had moved into a sibling. A grep does not fail loudly when the file is wrong; the string is simply absent, so a check written as "contains" quietly stops checking anything. (`a_branch_summary_is_handled_rather_than_dropped` did exactly that until it was found.) So a guard that must read code reads `crate::module_sources`: it walks a module's own `mod` declarations recursively, honours `#[path]` (`mod.rs` owns its directory, `name.rs` owns the sibling `name/`), skips `#[cfg(test)]` so a test's own copy of the string cannot satisfy it, and returns `(path, source)` pairs so a failure still names the file. `text_of` exists for a partition the walk cannot know about - `chat_keys.rs`'s picker arms moved into a sibling declared from the crate *root*, so no single root reaches both. `the_module_walk_reaches_every_ceiling_split_sibling` pins that the walk reaches what the guards need and does not reach `*_tests.rs`.

**Two refinements gh #552 added, both about a test binary rather than a source module.** First, `#[path]` resolves against the directory the *declaring file* is in — `std::path::Path::parent` — not against the module's own subdirectory. For `src/ext/mod.rs` the two coincide, which is why #543 did not notice; for `tests/provider.rs` they do not, so a `#[path = "provider/parity.rs"]` was being read as `tests/provider/provider/parity.rs`. It failed **visibly** (the file does not exist), so the fix is a walk bug rather than a silent-guard bug, and the assertion above now covers the test-root case. Second, a `#[path]` sibling is only needed at all because an integration-test root is a crate root, not a module: `mod parity;` there means `tests/parity.rs`. That makes a sibling inherit a **module segment in the test path** (`provider::parity::<row>` where it was `provider::<row>`), which the "identical test set" bar does not permit as-is — so the comparison is stated up front as *the set, with the new segment stripped, and the same count on both sides*. `include!` would have kept the old names, but it pastes items into the parent and hides them from the walk, which is the failure mode #574 was filed about; the names gave way instead, deliberately and in writing.

A regression test is written before the fix, following the same red-green discipline as any other TDD work: the test reproduces the defect and fails against the unfixed code, then the fix makes it pass. A pull request that fixes a defect without a regression test in the same change does not merge; this is a coding-standards rule, not a suggestion.

## 8. Property-based testing

Four invariants are specified here as the initial `proptest` target set; more are added as new stateful logic is written, following the same bar: an invariant that should hold across every input, not just the examples a unit test happened to pick.

Session log round-tripping: any sequence of valid records, written and then read back, produces an identical sequence, and a log truncated at any byte offset produces the longest valid prefix rather than an error, matching the recovery behavior specified in `docs/session-log-format.md`.

Compaction range integrity: a compaction extension's declared replaced range, applied to any generated session history, never causes a reader to lose a record outside that range, and a nested compaction, one whose range includes an earlier compaction marker, still resolves to a single coherent view.

Context-transform chain ordering: for any generated chain of transform extensions and any generated message list, the chain's output preserves the input's order except where a transform in the chain explicitly reorders, and a rejection at any position in the chain stops every transform after it from running.

Permission proposal hashing: for any generated proposal set and any single-field mutation of it, the stored hash comparison in ADR-0006's split store detects the change and triggers the difference prompt; it never silently accepts a mutated set as unchanged.

## 9. Cache behavior testing

This is the section the cache-preservation design in ADR-0017 exists to make testable, and it is worth treating as its own concern rather than folding into the general integration test list, given how central prompt caching is to what makes a coding agent affordable and responsive to use.

### What gets tested and how

Every scenario below scripts the fake provider with realistic usage numbers, runs a multi-turn session against it through the real agent loop, and asserts on the cache-waste figures the module from ADR-0017 computes from those numbers, the same way a real deployment would compute them from a real provider's responses. Nothing here needs the host to inspect request bytes; it needs the fake provider to report numbers a real provider would report, and the waste-detection logic to interpret them correctly.

A clean multi-turn conversation, no compaction, no model switch, no extension changes between turns, reports zero cache waste from the second turn onward. This is the baseline every other scenario is a deliberate deviation from.

A conversation that crosses the compaction threshold reports the compaction turn's own cost normally, since that prompt is genuinely new, and resumes reporting zero waste from the turn after, confirming the baseline reset behavior lands exactly on the compaction record and nowhere else.

A conversation where the active provider is switched mid-session reports the switch turn as counted waste, not exempted, matching the explicit design choice in ADR-0017 and in pi's own source. A test asserting the opposite, that a switch is silently exempted, would be testing the wrong thing; this scenario exists specifically to keep that distinction from eroding under a later, well-intentioned "fix."

A conversation that installs or enables a new extension mid-session, changing the tool list the provider sees, reports exactly one counted miss on the turn after the change and zero waste on every turn after that, confirming that a tool-set change is treated as a real, one-time prefix change rather than as ongoing waste or as invisible.

A `context-transform` extension that only appends content after the stable boundary produces zero waste attributable to it. A second, deliberately misbehaving transform extension that mutates content inside the stable boundary triggers the boundary-narrowing and extension-event recording behavior from ADR-0017 on the first affected turn, and the test asserts that the event is recorded, that the turn completes rather than failing, and that the boundary narrows to end before the earliest differing message. A third scenario covers the settling case: a transform that rewrites stable content deterministically, identically on every turn, records exactly one divergence and stops narrowing once its output matches the previous turn's, because cross-turn stability is what the provider's cache keys on, not input-versus-output equality.

A provider that never reports any cache activity across an entire scripted session, simulating a vendor or local server with no caching concept, reports no waste at all rather than reporting every turn as a total miss, exercising the "nothing to measure" distinction from ADR-0017 directly.

A miss below the 1024-token noise floor, adopted from pi's own calibration, is not counted, confirmed by a scenario scripting a small, deliberate prompt-size fluctuation under that threshold and asserting the waste total stays at zero.

### Why this belongs in the pipeline, not just in a developer's local run

A cache-hit-ratio regression is invisible in ordinary functional testing: every one of these scenarios produces a correct answer from the model, a passing turn, and a happy user, right up until the bill or the latency reveals that caching silently stopped working days or weeks earlier. The clean-conversation scenario above is promoted to a benchmark, not just a test: it runs in the same pipeline gate that checks binary size and cold start, asserting the computed cache-hit ratio across a canonical twenty-turn scripted session stays above a threshold (fixed at the Phase 3 exit test: **0.90**; the clean script itself scores about 0.97, since each turn's new tokens are paid and the rest is cache-read), and a regression here fails the build the same way a binary-size regression does.

## 10. Snapshot testing for cache-relevant assembly

Terminal rendering already uses snapshot tests against a virtual terminal buffer, per the software requirements and design document's own testing strategy. The same technique applies to something less obvious and specifically useful here: the assembled request.

For a canonical session state, fixed extensions, fixed history, no variation, the exact serialized message list and usage-relevant fields the host would hand to a provider's `stream-completion` call is snapshotted. A change to system prompt assembly, tool schema generation, or the transform chain that alters this snapshot shows up as a diff in review, and a reviewer sees plainly what changed and whether it was supposed to. This catches a category of regression the functional cache-waste tests above cannot: a change that would break a real provider's cache without ever showing up as a "miss" in a fake-provider test, because the fake provider was never told to care about the specific bytes that changed. The two techniques are complementary, not redundant: the cache-waste tests verify the waste-detection logic itself is correct, and the snapshot test verifies the thing actually being sent hasn't quietly drifted.

## 11. Requirements traceability

Every functional and non-functional requirement in the software requirements and design document should be verified by at least one test, and this is enforced mechanically rather than trusted to review discipline, since a missing test for a requirement is exactly the kind of gap that's invisible until it matters.

A test that verifies a specific requirement carries that requirement's identifier in a doc comment immediately above the test function, in the form `// Verifies: FR-CTX-3`. A CI check, run on every pull request, greps the full test tree for these markers, extracts every requirement identifier the SRDD defines, and fails the build if any FR or NFR has zero matching tests. It also flags, as a warning rather than a failure, any test marker referencing an identifier that no longer exists in the document, since a requirement that was renumbered or removed should have its test comment updated in the same change. The installer suite under `tests/install/` is shell and PowerShell rather than Rust, and carries the same identifier in a `#` comment; the extractor reads those files with the pipeline rule it already applies to `scripts/*.sh` and the workflow files, so a requirement whose only tests cannot be Rust is still a checked requirement.

This does not replace the qualitative judgment of whether a test actually verifies what it claims to; it only guarantees that every requirement has something pointed at it, which is the mechanical half of the problem and the half most likely to silently rot without a check.

## 12. Definition of done

A change is done when: a failing test existed before the implementation and now passes; the test's doc comment references the requirement, ADR, or defect identifier it verifies; a defect fix carries a regression test under `tests/regressions/`; an ABI-surface change updates the conformance extension in the same change; documentation affected by the change is updated in the same change, per the coding standards already in the software requirements and design document; and, specifically for anything touching message assembly, the provider call, `context-transform`, or `compaction`, the change has been checked against the cache-behavior scenarios in this document, either by running them or by a written note explaining why they don't apply.

## 13. CI execution strategy

Unit and integration tests run on every push, on Linux, macOS, and Windows, using `cargo-nextest`. Conformance tests run on every push in both delivery modes.

**Which bundled extensions are exercised through the sandbox** (gh #351 finding 3). The conformance probe is a fixture, not a product, so `crates/lca-ext-host/tests/bundled_wasm.rs` takes a *bundled* extension - one the CLI ships turned on by default - and diffs its answers between the committed component (loaded by `ExtHost::load`) and the crate's native handle: model listing, usage, login options and logout. Today that is **`openai-compatible` only**, chosen because it is the one bundled extension that ships a committed component and is already a dev-dependency of the host crate, so the diff costs no dependency and no build step. The next bundled extension is not covered: `compaction-default` has the native half in `lca-core`'s tests and no committed component, so adding it means either a new dev-dependency or a fixture the publish workflow refreshes. The same file's second row asks the committed component and a **fresh build** of the same source the same questions, which is the half `scripts/wasm-check.sh`'s interface comparison explicitly cannot see (a behaviour change that keeps the interface). Both rows read the artifact `wasm-check.sh` leaves in `target/wasm32-wasip2/release/` rather than building it - a nested `cargo` inside a test is a build-system dependency that turns a green suite into a flake - so they **skip by name** when it is absent, and `LCA_REQUIRE_WASM=1` turns that skip into a failure the way `LCA_REQUIRE_TMUX` does for the terminal suite. The flag is set in exactly the job where the artifact is guaranteed to exist - `extension components build`, right after `wasm-check.sh` has produced it - so a cold checkout there fails instead of reporting a skip as success, while the `engines` test-split group (where no artifact exists) skips honestly and says so in its log.

Property-based tests run a bounded case count on every push and an extended case count on a nightly schedule, since `proptest`'s value scales with iteration count and a full run on every push would slow the everyday feedback loop for no proportionate benefit. Fuzz targets run continuously on a dedicated schedule, not per push, with their corpora checked into the repository so a crash found once is a regression test forever after, not a one-time discovery. The fuzz crate is its own workspace, so no ordinary gate builds it and a parser change can leave a target uncompilable unnoticed until the nightly job dies at build — after the other targets have run their full budget. `scripts/fuzz-check.sh` closes that: the `fuzz targets build` CI job checks every target compiles on every push, without fuzzing. A fuzz target's assertions are contracts on the parser it drives, and cycle 4 broke two of them silently (a data-only manifest has no worlds; an archive may carry a bag instead of a component), so the contracts themselves are pinned as ordinary tests under `tests/regressions/`. Gate 11 is the file-size ceiling: `scripts/ceiling-check.sh` fails the build if any tracked `*.rs` file exceeds the workspace's 1,200-line limit and prints the offenders. It exists because the ceiling was breached twice by hand - the second time *after* the first was fixed by hand - which is a process gap rather than a discipline gap, so the check is a gate rather than a review note. The cache-hit-ratio benchmark and the binary-size and cold-start gates run on every push to `main` and fail the build on a threshold breach, per the release policy. End-to-end tests, being the slowest category, run on every push to `main` and on every pull request marked ready for review, not on every intermediate commit. The live-smoke workflow runs on its own schedule against a real provider and skips cleanly when its key is absent (NFR-23), so it is the guard against the transport-shape class of defect that a fake provider cannot see. Real-terminal tests run only on the platform that owns their harness — the tmux suite on the Linux job, the ConPTY suite on the Windows job — and everywhere else they skip with a named reason rather than fail; see section 14.

A flaky test is quarantined, not ignored: it is marked and excluded from the required check within one working day of being identified, with a tracking issue, and a quarantined test past a set age without a fix blocks new quarantines from the same crate until it is resolved, so quarantining doesn't quietly become the normal way tests are handled.

## 14. Real-terminal testing in depth

Virtual-buffer tests cannot see the terminal-shaped failure class: a secret that leaks into the visible frame, a resize that leaves a stale row, a control sequence from hostile content that corrupts the display. Real-terminal tests close that gap by driving the agent inside an actual terminal and asserting what is on the screen.

Two harnesses, one checklist. Unix runs the agent in a tmux pane and asserts through `capture-pane`. Windows runs it under a pseudo-console (ConPTY) and asserts through the console buffer; ConPTY is chosen deliberately, because its quirks are the known breakage surface of the Windows terminal path. Both harnesses assert the same behaviors: startup renders the frame; a scripted turn streams and renders, with the first delta painted before the turn ends; the permission modal appears and answers; the secret prompt masks its input (no key bytes in the visible frame); a drag selection highlights and copies the selected text (a verified native clipboard when one exists, else OSC 52 written unverified); a markdown answer shows aligned tables and framed code blocks and no half frame mid-stream; a resize re-renders; a clean quit writes `session-end` and leaves the session resumable.

**The paste rows (cycle 7, R6/R1).** Paste and mouse capture are the two things `send-keys` cannot exercise, because `send-keys` synthesizes key events — typing by another name. Every text surface therefore has a row, driven with `tmux load-buffer` + `paste-buffer -p` (the `-p` is required: without it tmux sends the buffer as *typed input*, and a multi-line paste submits line by line — that is how this gap shipped): **editor**, **the masked secret field**, **the base-URL field**, **the model-id field**, **the `/resume` and `/model` picker searches**, and **the transcript search** × these paste shapes: a single line; multiple lines (flattened in a single-line field, marker in the editor); embedded CRLF and tabs; 10+ lines (editor marker row); one huge line (`[paste #N N chars]` marker); and a trailing newline. The secret row asserts the pasted value is masked and that its bytes never appear in any frame — the same §14 mask check, now driven through the paste channel instead of the key channel. Three raw-input rows cover what `send-keys` also cannot reach: **fragmented bracketed paste** (`ESC[200~`, content, `ESC[201~` in separate writes, exercising `stdin_buffer`'s reassembly and its dual 50/10 ms timeouts), the **tmux CSI-u paste dialect** (`ESC[<cp>;5u` re-encodings inside the paste, decoded by `lca_tui::widgets::paste`), and an **unbracketed flood** with bracketed-paste mode never enabled (pasted text is indistinguishable from typing; it must be treated as input). The mouse rows assert the DEC-mode contract as a pair: the main-screen renderer emits **no** mouse-enable sequence, so native selection and right-click paste survive; the alt-screen renderer emits exactly pi's set, so selection belongs to the renderer. Which one is the default flipped back to alt-screen on 2026-10-01 (ADR-0037's second annotation), so the rows assert each mode's contract rather than the default's.

**The dialog-style and caret rows (cycle 8, R4/R5).** Two unit rows hold the rendering contracts: a dialog row over a strongly painted transcript line is asserted to carry a reset, the border role's SGR, and a trailing reset (so nothing inherits), and the fragments outside the dialog are asserted to keep their own bytes. For the caret, a frame whose only difference is the caret column is asserted to repaint the caret's row and place the column, in both renderers, while leaving untouched rows alone - and a real-terminal row reads the *pane's* cursor column (`tmux display-message '#{cursor_x}'`) after each space keystroke, which is the receipt the owner's report asked for.

**The thinking-visibility rows (cycle 8, R6).** Four transcript-level rows cover the shapes - snippet (three lines plus `… +N lines`), the in-place expansion of a run, `full` and `hidden` as settings values, and the per-run rule (toggling the latest run leaves the earlier one on its setting) - and a real-terminal receipt shows the default snippet in a live pane. Mouse click-to-toggle is not implemented: the transcript has no per-row hit testing in either renderer, and the keybinding covers the action; recorded in the cycle report rather than left implied.

**The parity rows (TUI-10, M1-M6).** The chat-rendering parity cycle added five real-terminal receipts beside the unit rows: an **OSC 8 link** captured with `capture-pane -e` while `LCA_HYPERLINKS=1` forces the capability on, so the escape bytes (ST-terminated, URL inside, nothing printed inline) are on the record, plus its `text (url)` fallback with the override off; a **display math fraction** stacked over its rule; a **mermaid diagram** rendered as art rather than a fenced block; a **task list** with its authored markers; and a **streamed partial fence** read mid-turn, before the closing backticks arrive, asserted to show code-so-far with a balanced frame. The same pane sessions feed the side-by-side with pi in the cycle report, one message exercising all five.

**The permission matrix (cycle 8, R10).** Three columns, proven on a real terminal with the session log as the evidence: **ask** (the existing modal row - a review-class command prompts, `o` lets it run, and the log carries `decision: once`), **read-only auto** (`a_read_outside_the_workspace_does_not_prompt`: a `read` of a path outside the workspace completes with no modal and leaves no `permission` record, because no decision was made), and **yolo** (`yolo_approves_without_a_modal_and_records_the_decision`: `--yolo` shows the banner, runs the same review-class command with no modal, and the log carries `decision: always` with the exact action - the same record a human "always" answer writes).

**The caret and composer rows (UI/UX phase 1).** Four rows. A real-terminal receipt captures the caret *painted into the row* - the reverse-video cell after `CURSOR_MARKER`, with the hardware cursor positioned but hidden - which is the row that proves issue #10's "spaces are invisible" fix on a live pane; the painted column is asserted per keystroke on the fake terminal (`a`, space, space, `Home`, `End`, a letter: the keystroke matrix), and the layout rows cover trailing spaces, a wide grapheme, and a ZWJ cluster. The history boundary matrix (a two-line prompt, Up/Up/Up then Down x4) asserts buffer-versus-history at every step, per pi's rules. A second real-terminal row drives the freeze sequence from issue #20: a slow tool call holds a turn, `/settings` is submitted mid-turn, the selector must open *while* the status still says `running` (it was the dump's notice before gh #30), and `Ctrl+C` must still cancel - negative-tested against the pre-fix tree, where the row fails at the five-second wait.

**The color rows (cycle 9, R1-R3/R5).** Two layers. At the frame level, unit rows assert exact SGR on the fake terminal: the user band is painted `userMessageBg` on every row of the message and each row is exactly the render width; a tool card carries its state's background in all three states (`toolPendingBg` running, `toolSuccessBg` settled, `toolErrorBg` failed), each row full width; the separator is asserted per state (idle dashes, `Working` painted end to end in `separator_border`, `Retrying (n/m) in Ns…` with the warning spinner and a muted label), each exactly one row of the requested width including the narrow cases; a fenced rust block is asserted to carry the comment, keyword, string, and function roles at once; and the theme's own style functions are asserted to close only the channel they opened (`39`, `49`, the decoration's code), with a banded row asserted to contain no full reset. The plain theme has its own row: no SGR at all. On a real terminal, `e2e_color.rs` drives one session through a pending command, a settled one, a failing read, and a fenced block, and reads each receipt back with `capture-pane -e` (the harness gained `capture_e`/`wait_for_e` for this): the band, all three card backgrounds, the working separator as one color end to end, the idle separator after the turn, and the four syntax classes inside one block. The side-by-side with pi is in the cycle report.

**The image-header rows (gh #358).** Image dimensions are parsed from a header without decoding, and that parser runs on every transcript render and resize — so a panic there is fatal rather than recoverable. The guard is a full truncation matrix (every length 0..=30 per WebP chunk kind, plus empty input) asserting the placeholder path instead of a panic, the three positive dimension rows per chunk kind, and two `proptest` properties over arbitrary byte buffers. A real-terminal row attaches a 20-byte truncated `.webp` and asserts the pane survives and renders the attachment stub; on the pre-fix tree that row fails because the render panics and the session dies before `attached` is printed.

**The `/tree` layout rows (gh #394).** The navigator's geometry was wrong in a way only a screen shows: one gutter per visible ancestor indented a plain 40-turn session 160 columns deep. Two real-terminal rows in `crates/lca-cli/tests/e2e_tree_layout.rs` now drive a 60-column pane - every painted row of a long linear session at the same column, with no connector and no gutter, and a forked session whose window shows the `├─`/`└─` pair and answers `Alt+←` with a `⊞` fold - and the frame-level rows live in `crates/lca-ui/src/chat_tree_tests.rs` (flat chains, fork grouping, active-trunk order and determinism, ancestor-anchored re-filtering, recompute-after-filter, fold glyphs, dual-action keys, pinned-gutter panning, tool-call labels, the live-leaf exemption). `tests/regressions/394-tree-layout-math.rs` is the shipped-defect guard: it builds a real 80-record session through the store, maps it the way the CLI hook does, and asserts the painted frame, failing on the pre-fix geometry.

**The rows this phase's manual driving added.** Two unit rows hold what only a human saw: a denied tool call is announced before it settles (and the session log's `tool-call` precedes its `tool-result`), and a queued message that flushes as its own turn keeps its queue marker in `Record::User.queue`. Two more hold the side-by-side findings: a heading renders its inline tokens in the heading style with the style re-armed after a nested reset, and a table's header cells are bold while its data cells and border are not. One more holds what a live pane showed and only a live pane could: a background `/compact` reports `Idle -> Running -> Done` through its poll hook, so the working state rises once, `Running` does not repaint on every tick, and the result is announced exactly once. The manual matrix itself - separator animation, band repaint on a theme change, the permission modal over a painted band, the plain theme with zero SGR, resize, fullscreen, the retry separator - is recorded per step in the cycle report: a checklist, not a gate, and every item on it that *is* gated has a row above.

Platform gating is part of the contract, not an afterthought. tmux has no Windows build, so the Unix suite is `#[cfg(unix)]` with a runtime probe for tmux, and the Windows suite is `#[cfg(windows)]`. A machine without its harness skips these tests with a named reason and never reports a failure for the tooling's absence; a platform that lacks a harness is recorded in `docs/platform-notes.md`, so an absent run is always a documented state. On CI the probe is strict: the macOS leg installs tmux and every test-split leg exports `LCA_REQUIRE_TMUX=1`, which turns a skip into a named failure, and the macOS shell leg additionally asserts at least one executed real-terminal row in its log (#104) — a leg that passes while exercising none of the terminal contract is the bug being gated.

These tests use the fake provider, like every category except the env-gated live smoke: a real terminal does not require a real model.

The harness itself has a contract, because the tests' honesty depends on it (gh #413's class; six ledger entries for one row and two false fix-up hunts). Three rules:

- **The socket is per test binary.** Its name carries the process id (`lca-tui-test-<pid>`), never the default socket and never one shared name, so two suites — two worktrees, one machine — cannot drive each other's tmux server. The server is killed at process exit, so no socket files accumulate.
- **An empty pane is a harness condition, a painted pane is a fact.** When a budget expires on a *blank* pane the terminal never came up: the wait re-spawns the same named session once, with the same command, says so on stderr, and re-polls a bounded second time. When the pane *has content* but lacks the expected text, the wait fails as before — that is a real product failure, and hiding it behind a retry would be the worst of both.
- **Waits are fold-aware.** A selector paints its rows over several frames, so a row that must be asserted is *waited for*, not slept through: `wait_for_all` waits until every needle the assertion reads is on screen in one frame. Waiting for one label and asserting a second raced the render; the assertion itself is unchanged.
- **An absence-asserting wait needs a positive half.** A wait of the form "nothing violates X" is
  **vacuously true on empty input**: `wait_for_layout_width` returned as soon as `widest <= cols`, and a
  pane that had not painted yet measures **0**, so `0 <= 60` held and it reported a blank frame as a
  correct layout (gh #489's second round — four consecutive red CI attempts, green locally 6/6). Every
  harness wait that asserts an absence (no line too wide, no leaked process, no stray socket) must also
  require that *something was observed at all*, which is the same rule `retry_once` documents: a `None`
  means "the precondition was not met", never that the assertion held.
- **A wait's budget scales with machine load, on every platform (gh #589).** The caller's timeout is a claim about the *product*; a pane that has not painted says nothing about the product, so the harness multiplies the polling budget by a load factor (1x below light load, capped at 4x). This is measured rather than guessed: a WASM-bearing session takes 21-23 s to first paint on an idle four-core box (the component JIT), against the 30 s budgets the rows carry, so two suites at once would otherwise fail perfectly correct rows. **Which signal answers depends on the platform, because the original one was Linux-only:** `/proc/loadavg` does not exist on macOS or Windows, so until gh #589 the factor there was hardcoded to 1x — the allowance was real on the developer's box and absent on the two runners that needed it. Linux still uses the load average (unchanged, and it pays nothing extra); macOS and Windows measure **scheduling overshoot** instead — three 20 ms sleeps whose overrun is the signal (an idle box overruns by a fraction of a millisecond, a runner timesharing at a 60-80 ms quantum overruns by most of one). The rule is two pure functions (`factor_for_load`, `factor_for_overshoot`) selected by `factor_from`, which is what lets the macOS branch be tested on Linux; the probe runs once per process (`OnceLock`), and `LCA_LOAD_STATS=1` prints the factor and which signal produced it. What scaling does *not* do: a pane with **content** that never shows the needle still fails, and a **blank** pane is still the one case that re-spawns once — the factor widens how long the harness polls, never whether a wrong frame is a failure. (The previous wording here said a painted-but-wrong pane was "judged at the caller's original timeout"; it was not, and the corrected sentence is above.)
- **The socket directory is asked of our own socket, never the default.** `tmux -L <our socket>` reports its path whether or not the server is up; probing the default socket would race two binaries on it and put test traffic on a developer's own tmux — the exact rule this harness exists to keep.

The contract is pinned by `crates/lca-cli/tests/harness_contract.rs`, which drives fake commands (a blank pane that heals on the second spawn, a painted pane that must fail) so the harness's own behaviour is tested without a product binary.

**Readiness primitives (gh #447's family, five rows).** A second class of harness failure is not about budgets at all: a row asks the pane one question and treats the answer as complete. `wait_for(head)` returns the frame the head was painted in, so a row that then asserts a *second* glyph is reading two moments as one (`e2e_picker_scroll`'s `╭`, `e2e_tree_navigator`'s pair of connectors, `e2e_color`'s separator). And `[session in` is painted by the first render, which says nothing about the input thread: a scenario typed in that gap is lost, and lost input is invisible to every later poll (`e2e_slash_output`'s `/hotkeys`, `e2e_model_consent`'s 0.82 s failure). Three primitives in `crates/lca-cli/tests/common/readiness.rs` close those classes once, so the next row does not invent its own sleep:

- **`wait_until_painted` / `wait_settled_for`** capture until two consecutive frames are byte-identical and return that frame; the `_e` variants settle in the SGR capture kind so a colour receipt cannot come from a frame older than the one that settled. The needle-anchored form is the one to reach for: settling alone will settle on a screen that has not painted the row's content yet.
- **`wait_for_input_ready`** types a process-unique probe token, waits for it to be *echoed* (which can only happen through a live input path), then erases it with one backspace per character and re-reads to prove it is gone — so the probe never becomes the scenario's first words. It proves the pane is echoing, not that `lca` is the program echoing, so rows still wait for their product marker first; the primitive closes the gap between "the marker was painted" and "keys reach the reader". And it cannot be used on a **masked field**, which does not echo by design: call it once after spawn on the ordinary composer, before opening a no-echo surface — that attachment is the same process-wide input path the later field uses.
- **`retry_once`** is the `conformance_diff.rs` house pattern promoted, lazy by construction: a passing first attempt is not duplicated (a tuple would run the journey twice), and a second miss is final so a broken row cannot spin. `None` means "the precondition was not met", never "the assertion failed" — an assertion still panics, and a panic is not retried.
- **`wait_for_layout_width`** waits for a *resize to have been applied by the application*, not for the pty to take it. Its width is measured on the **plain** capture, never `-J`: a row the app pads to exactly the pane width fills it, so tmux treats the next row as a continuation and `-J` concatenates them - a healthy 60-column pane reports 140 that way, and that false reading cost gh #522 a full investigation. The signal it uses instead is *wrapping*: a run of consecutive rows that each fill the pane means content is spilling past it. `Tmux::resize` used to be `tmux resize-window` plus a fixed 500 ms sleep; the pty takes the new size immediately (a shell inside sees it on the next read) but the application re-lays-out on SIGWINCH from its stdin reader loop, which under a parallel suite can exceed half a second. A row then ran its whole scenario against the previous, wider layout — and the failure was nearly invisible, because tmux soft-wraps an over-wide frame so every *physical* line still fits the pane. The primitive polls the **joined** capture (`capture-pane -J`, which undoes that wrap) until no logical line is wider than the requested width. This is the one readiness primitive that reads the *layout* rather than the content, and it is a wait rather than a longer sleep for the same reason as the others: a sleep would be the same guess with a bigger number.

  **A blank pane is not a layout that fits** (gh #489 follow-up). The width of a pane that has not painted is `0`, and `0 <= cols` held — so the primitive returned an empty frame and reported the layout correct, which is the same vacuity from the inside that the row above it hit from the outside (`measured 0`). `Tmux::resize` waits through this primitive, so a row's *setup* could return instantly against nothing and then assert on the empty screen it was handed. A blank capture is now treated as "not yet", exactly like an over-wide one: the wait is bounded, the failure says which of the two conditions it was (an empty screen is a harness condition and gets one re-spawn, matching `settle`), and the negative direction is unchanged — a painted 140-wide frame still fails a request for 60. The rule for a row: **a fixture precondition is waited for, never assumed.** `wait_until_painted` before reading `logical_width()`; a row that asserts a precondition without establishing it is asserting about the runner's speed.

**A two-paint fixture must not own its gap with a `sleep`** (gh #489's third round, the third red `main` in this one family). `harness_contract`'s positive settle row spawned `echo head; sleep 0.1; echo border` and asserted the settled frame carried both — which asserts that a forked `sleep` plus the shell's own scheduling will not stretch past `POLL` (150 ms). On an idle box that holds: measured here at load ~18 after the fact, the old fixture's gap ranged **9–163 ms**, four of twenty-four samples within 2x of the poll and one *past* it. On a loaded macOS runner it does not, two consecutive captures land inside the gap, the loop declares the head-only frame settled, and the row fails. So the gap is now a **relay**: the fake blocks on `read`, the row releases it with a keystroke, and the length of the pause is the row's decision instead of the scheduler's. What a relay gives up is stated in the row: it can no longer prove *by timing* that it observed the intermediate frame, so the ordering half moved to two rows that are deterministic rather than lucky — a settle costs at least two captures, and a screen that keeps moving keeps the loop polling. The general rule: a fixture's phase boundary is a handshake the test owns, never a duration, because a duration is a claim about the machine the suite happens to run on. `no_two_paint_fixture_trusts_a_sleep_for_its_gap` enforces it structurally — it reads this file's own source and fails on any two-paint `spawn_raw` without a `read` — since a threshold on the gap would just be another wall-clock assertion of the class that has now failed here three times.

**A wide row must be painted in one write** (gh #587). `harness_contract`'s wrapped-cap fixture emitted its 140-cell row as 138 separate `printf`s, one dash each — so between the `╭` write and the last dash the screen genuinely stops changing for longer than the settle's poll interval, and `wait_until_painted` declared a frame of `╭` plus 19 dashes "painted" and the row measured 20 cells. That is not a product width; it is a row still being composed, and under load the 138 writes take longer, which widens the window — which is why it appeared only inside a full workspace run. `settle` cannot tell "still composing the row" from "finished", and it deliberately does not try: a real app frame legitimately has an unclosed `╭` mid-render, and `settle` serves every e2e row, so a heuristic there would redden healthy rows. The rule is at the **fixture**: build the whole string, then `printf` it once, so no intermediate frame exists at any load. The row then waits on the fact it asserts rather than on the mere absence of change - it re-settles (bounded, ten settles) until the frame it read already measures wider than the pane, which is the assertion's own condition, so the loop cannot hand the assertion a frame it would reject. Anchoring on the cap's closing corner instead is **not** enough, and that is measured rather than assumed: tmux mid-wrap of an already-painted 140-column row settles on one of the cap's screen rows by itself, so a frame with `╮` and no `╭` still measures 20 (4 of 6 runs). `a_wide_row_fixture_paints_in_one_write` keeps any future wide-row fixture from going back to a per-character loop.

The honest limit is documented and pinned rather than assumed away: **two identical frames is a heuristic, not a guarantee.** A pane that pauses longer than the poll interval between two paints looks settled, and `a_pane_that_pauses_past_the_poll_interval_looks_settled` records exactly that, alongside the remedy that works (anchor on the needle with `wait_settled_for`). What would catch it if it ever bites: a longer quiet window, or asserting on a state marker the app emits instead of on the absence of motion. A live animation is the other side of the same coin — `e2e_color`'s in-flight read keeps `wait_for_e`, because a spinner's frame legitimately never repeats and settling there would time out; the two-frame rows that needed settling are its post-turn reads.

Every primitive changes *when* a row reads, never *what* it asserts. Each has a positive row and a negative row in `harness_contract.rs` (a fake that settles, a fake that never settles and must **fail** with both frames in the message rather than hang; a fake that echoes, and a `stty -echo` pane that never does and must fail with a message naming what a lost scenario means). `tests/regressions/447-*.rs` is the NFR-24 guard that the primitives exist and keep their negative behaviour, so a future simplification back to `sleep`/`wait_for(glyph)` fails.

One row in this family needed a different fix in kind, because a longer window cannot help: `lca-mcp`'s `an_oauth_flow_host_does_not_survive_into_tool_traffic` polled the flow-scoped host set every 5 ms from *outside* the flow and returned at the first non-empty sample, so a fast runner could finish the whole sign-in before the first tick and `during` was legitimately empty — the row raced its own instrument, and no sampling period can pin "it was admitted during the flow" if the flow can be shorter than the sample. It now reads the host set from the **browser opener**, which `oauth_open` invokes synchronously inside `sign_in_flow`, after both attach waves and before the set is cleared: a fact about the flow's own body that cannot miss and cannot observe an after-state. Reading it outside instead fails the row, which is what keeps it honest.

**A countdown is a promise, so a row asserts the effect, not the paint** (gh #592). The permission modal announces `auto-approves in Ns`, and the issue reporting it "painted but not kept" turned out to be a **reading** defect rather than a product one: two modals were on screen in sequence (an unconsented endpoint's net consent, then the shell permission ~30 s later, each with its own fresh `29s`), so a capture at "+28 s" was the second modal's second, not a stale first. Measured on this box at load 6-18 with spinners running: the modal paints at **+0.7 s** showing `29s`, its printed second advances **29, 28 ... 0** on every 0.5 s capture, it closes at **+30.4 to +30.7 s**, and the tool's own side effect lands at **+30.4 s** with no keypress. `crates/lca-cli/tests/e2e_permission_countdown.rs` is the row, and it asserts three things in order: the second advances to `0` (a frozen number fails), the modal closes inside the countdown plus 2 s, and the tool actually ran at the announced second (its marker file's mtime, so the assertion does not have to trust a rendered timestamp). Three things about it are the rule and not the row: **the countdown is never shortened** (the row reads the product's own 30 s, because a test that moves the deadline stops testing the promise); **the panel keeps painting while the modal waits** (`tick_permission` returns "the modal is still up" so the loop requests a frame - a mutant returning `false` there stays green on the effect and leaves the countdown frozen, which is why the advancing-second clause is separate from the effect clause); and **the modal only exists in `ask` mode and only for a command the analyzer refuses** - the row writes that mode into the user config rather than inheriting the shipped default, and its command carries a `$( )` substitution because a trusted project auto-approves workspace-scoped commands (`is_allowed` -> `trust.allow`, ADR-0039), so a plain `touch` would test the trust path instead of the countdown. The #594 row's 45 s budget is unaffected by this cycle: nothing changed when the deadline is set (still `now() + 30 s` at modal construction), and `e2e_compact_budget_594` is re-run beside the new row as the receipt.

**Per-test budgets are measured, never guessed (gh #429).** The default ceiling is 60 s slow / 120 s terminated, which is right for a row that hangs. A row legitimately slower than that gets a *scoped* override in `.config/nextest.toml`, filtered to its exact test name so siblings and future rows keep the default, and carrying the measurement that justified it: for `e2e_install`'s Phase 5 exit test the comment records the stage breakdown (0.12 s of fixture setup, 94% of the row in two turns at ~12 s each), the cause (`wasmtime::component::Component::new` costs 21.8 s in a test build against 1.7 s in release for a 558 KB component, so every turn-shaped spawn pays a compile), the seven loaded samples, and the arithmetic `worst × 2`. Two rules follow from that row. First, measure the stages before choosing between a budget, a split, or shared setup: the doubling-cancels theory was wrong here, because the doubled part was 0.12 s of 42 s and no amount of sharing touches a per-process compile. Second, a raise that is blanket, or large enough to hide a future regression, is not a fix; the number has to be re-derivable from the comment by the next person. Scoping is verified behaviourally, not assumed: a throwaway sleep in a sibling row must still be terminated at the default while the overridden row survives. A budget is the last resort, not the first (gh #449): when the same profile showed two `conformance_diff` rows at 73-77 s, the cost was three and two `Component::new` compiles inside rows that only needed one, so deleting the redundant loads halved the whole file (110 s to 66 s) and no override was added at all. The test is whether the row is doing work it needs; only a row that already does the minimum gets a ceiling. A structural guard pins that count rather than the wall clock, because a stopwatch assertion on a row's duration re-creates the load-sensitivity the budget exists to tolerate. Where a row's *claim* really is elapsed time, the bound is carried per platform with its measurement beside it — and it is derived from the interval the defect costs, not from the observation, because **a bound finer than the platform's scheduling quantum is not a bound on that platform**. `docs/platform-notes.md` records that family (gh #588's three macOS rows) with the numbers and the derivation.

## 15. Installer tests

The installers are product surface (SRDD `FR-INSTALL-*`), so they get their own suite, their own CI job, and their own gate rather than being folded into an existing category: `tests/install/test_install_sh.sh`, `tests/install/test_install_ps1.ps1`, and `scripts/install-check.sh`, the last of which is gate 10 in `docs/release-policy.md`.

The suite is hermetic by construction. It points `LCA_BASE_URL` at a fixture directory laid out like a release (`latest/download/`, `download/v<V>/`, and `download/unstable/` with a hash-version asset) containing fake assets and a real `artifacts.sha256`, sets `HOME` to a scratch directory so no real rc file or install directory is touched, and shadows `uname` with a stub earlier on `PATH` so all four sh platform mappings run on one machine. Nothing in the sh suite makes a network request; the only networked checks in this area are the post-push manual runs recorded in the cycle's report file (the exact README one-liner against the real raw URL), which are evidence, not gates.

What the sh suite asserts, one test function per SRDD identifier: the four platform mappings select the right asset (FR-INSTALL-7's positive half); an unsupported platform exits 2 with the PowerShell pointer (FR-INSTALL-7); a checksum mismatch refuses and leaves an already-installed binary byte-identical (FR-INSTALL-2, FR-INSTALL-1); a fresh install places an executable binary and writes exactly one marked rc block (FR-INSTALL-1, FR-INSTALL-3); a re-run over an install is idempotent — one block, `old -> new` reported (FR-INSTALL-3, FR-INSTALL-4); `--uninstall` removes the binary and the block and nothing outside the markers (FR-INSTALL-5); `--no-path` leaves the rc file byte-identical (FR-INSTALL-3); a failed download leaves an existing binary in place (FR-INSTALL-1); `--version` resolves the pinned directory (FR-INSTALL-8); `LCA_BASE_URL` is the only thing the fetch path consults (FR-INSTALL-6); and the unstable line (FR-INSTALL-10) resolves `download/unstable` for both the binary and its checksums — the stable directory's checksums are poisoned in that fixture, so consulting them at all fails the row — `--unstable` with `--version` exits 2, and the round trip reports `0.0.0 -> 0.5.2.b6573049 -> 0.0.0` both ways. Assertions are on `grep`, `cmp`, `test -x`, and exit codes — the same discipline as the rest of the tree: no snapshot of a human-readable message unless the message is the contract.

The PowerShell suite runs on `windows-latest` under both shells the requirement names, Windows PowerShell 5.1 (`shell: powershell`) and pwsh (`shell: pwsh`): the same fixture shape with `-BaseUrl`, hash-mismatch refusal, install, the re-run's `old -> new` report, pinned version, uninstall, and the unstable rows (FR-INSTALL-10) — flag, poisoned-checksum proof, mixed-flag exit 2, and the hash-version report, the last of which builds a fixture exe with `Add-Type` where that shell can compile one and records a named skip where it cannot — plus direct assertions on the PATH join function's idempotency and non-clobbering behavior, because reading a live registry back is not a stable assertion on a runner shared with everything else the job does. Where a behavior genuinely needs the registry (`-NoPath` leaving `Path` untouched) the test runs against the user `Path` of the ephemeral runner account, which is exactly what a real user's first run edits.

The gate (`scripts/install-check.sh`) runs the sh suite and `shellcheck --shell=sh install.sh` and is registered in the CI `install` job on all three platforms. A machine without `shellcheck` reports it as a named skip rather than a silent pass, matching the harness-absence rule in section 14; the CI job runs on a runner that ships it (`ubuntu-latest`), so the gate is never skipped where it matters.

## 16. The shell tool's fidelity corpus

The `shell` tool's transport is the one place where a defect produces a command that is *not* what the model wrote - a mangled quote, a dropped line - and a wrong result that reads as the model's fault. ADR-0041 fixed the Windows transport (a per-call script file); this corpus is what keeps it fixed.

The rows live in `crates/lca-tools/tests/shell_fidelity.rs`: a command, the markers that prove every part of it ran, the mangled forms that must not appear, and, where the row cares, the exact bytes of a file the command writes. They cover multi-line commands, double and single quotes, real newlines, trailing spaces, shell metacharacters (`& | ; < > ^ ( )`), backslashes, unicode, an ANSI snippet, CRLF text, empty lines, and each shell's variable syntax (`%VAR%`, `$env:VAR`, `$VAR`). A row passes only when the command runs through the **real executor** - a plan-level assertion would not have caught the defect that lived in `CreateProcess` quoting.

Where it runs: the POSIX rows on every `cargo test` on Linux and macOS, and on Windows through the Git Bash leg; the `cmd` and PowerShell rows on `windows-latest`, once per interpreter the ladder resolves (all four are present on that runner). A missing interpreter is a named skip with its reason, never a silent pass. The Windows ladder itself, including the WSL-stub trap, is unit-tested on every platform through the `Probe` trait, which is how a Windows-only trap stays covered on a Linux runner.

Property tests (`proptest`, `crates/lca-tools/src/shell.rs`) carry the invariants for arbitrary command text, not just the corpus: the POSIX script text is the command byte for byte, argv never carries a multi-line body (the invariant the requoting bug violated), and cmd's script text differs from the command only by line-ending normalization.
