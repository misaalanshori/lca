# Inspiration and provenance

Version 0.1, 2026-09-20.

This document names what in LCA's design comes from studying two existing projects, a coding agent called Pi and a native-binary agent called fx, and what doesn't come from either. It exists so a contributor, human or agent, working from this document set alongside the source of both projects can tell which parts to study closely, which to treat as loose inspiration, and which to leave alone because the decision here already diverged from both on purpose, with the reasoning written down elsewhere.

Read this alongside the two projects' actual source, not instead of it. Where this document names a specific file or module, that's a pointer to go read, not a description complete enough to substitute for reading it. Nothing here should be ported by translating syntax; Pi is TypeScript and fx is Zig, and this project is Rust with a WIT-typed WASM extension ABI neither of them has. The thing worth taking is the design a piece of code encodes, not its text.

## The short version

This is, in large part, a Rust port of Pi. Pi's architecture, its minimal-core philosophy, its testing discipline, and specifically its approach to compaction and prompt-cache efficiency are the primary reference throughout this document set. Where this design differs from Pi, the difference is almost always the WASM sandbox and capability model, which Pi doesn't have and doesn't need for its own trust model, layered on top of behavior that is otherwise Pi's. fx is the secondary reference, contributing the native-single-binary architecture and proof that compiling the same agent to both a native target and `wasm32` for JS-host embedding works, but fx's own extension story is much thinner than what this project builds; treat fx's source as validation that the native-and-WASM combination is buildable, not as a specification for how the extension system itself should work.

## From Pi: the minimal-core philosophy

Pi's own stated design, in its usage documentation, is a small core with workflow-specific behavior pushed into extensions, skills, and packages, explicitly naming MCP, sub-agents, permission popups, plan mode, to-dos, and background bash as things it deliberately does not build into the core. This is the direct ancestor of ADR-0013's three-way split between fixed core, build-time-swappable backends, and runtime extensions. The difference is that Pi's extensions run as plain, unsandboxed TypeScript with full process privilege; this design keeps Pi's instinct for what belongs outside the core while adding the capability-gated WASM boundary Pi never needed, because Pi's trust model is "review the source before installing," stated plainly on pi-antigravity's own page, and this project's is not.

Pi's core built-in tools, `bash`, `edit`, `find`, `grep`, `ls`, `read`, `write`, and a separate `powershell` tool for Windows, are the direct model for keeping read, write, and shell tools as ungated core with a swappable backend rather than a capability-gated extension, per ADR-0013's classification table. Study Pi's tool implementations under its core tools directory for the shape of a well-scoped built-in tool: what it validates, what it truncates, what error shape it returns on failure.

## From Pi: the package split

The very first design decision in this document set, the fifteen-crate workspace in ADR-0002, was made because Pi's own monorepo splits into focused packages, `agent`, `ai`, `coding-agent`, `chord`, `client`, `protocol`, `server`, `session-backends`, `telemetry`, `tui`, each with a clear single job and a clean dependency direction. Study Pi's package boundaries, particularly the separation between its provider-facing `ai` package and its agent-loop-facing `coding-agent` package, as the direct model for this project's own `lca-provider`/`lca-core` split.

## From Pi: providers, and pi-antigravity specifically

Pi's `pi-ai` package wraps a wide set of providers with OAuth support for several subscription logins, Claude Pro and Max, ChatGPT Plus and Pro, GitHub Copilot, xAI, OpenRouter, and Radius among them. This breadth is the reason the provider world was designed as an extension point from the start rather than a fixed set the core knows about.

pi-antigravity specifically is the closest thing to a full specification the Antigravity reference provider under `extensions/antigravity/` has. Study it directly for: the loopback OAuth callback mechanism, which is the model for the `oauth` capability's `begin`/`await` shape; how it stores and refreshes tokens, the model for the `credentials` capability's namespace isolation; its custom commands, `antigravity.doctor`, `antigravity.usage`, `antigravity.models`, `antigravity.image`, `antigravity.refresh`, which motivated promoting `usage` specifically to a world-level export in ADR-0012 rather than leaving every provider author to invent their own naming; and its own explicit security note, that installing a Pi package means trusting arbitrary code, which is the exact sentence this project's capability model exists to make untrue for the WASM delivery mode.

## From Pi: compaction, logically not physically

Pi's compaction, confirmed by reading its actual session and compaction handling, does not rewrite stored history; it changes what's sent to the model on a given request while keeping the underlying log intact. This is the direct source of `docs/session-log-format.md`'s design: an immutable, append-only log where a compaction record marks a replaced range and a reader substitutes a summary, never mutating anything that came before. Pi's own `custom-compaction.ts` example extension, demonstrating that its compaction strategy is itself swappable, is the direct precedent for making `compaction` its own extension world in ADR-0015 rather than a fixed host algorithm.

## From Pi: cache-waste measurement, adopted directly

`cache-stats.ts`, in Pi's core, is the single most directly borrowed piece of design in this whole document set, and ADR-0017 says so explicitly. Read that file before implementing the equivalent module here. The specific things taken, not just the general idea: computing missed tokens by comparing a turn's prompt size against the previous turn's and subtracting what was actually read from cache, rather than hashing or comparing request content directly; resetting the baseline specifically on a compaction event, treating it as legitimate re-billing rather than waste; explicitly not exempting a model switch, on the reasoning that it re-bills the full prompt and that cost is real and worth surfacing; the 1024-token noise floor, below which a miss is breakpoint-granularity noise rather than a signal; and the distinction between a provider that has never reported cache activity at all and one that reported activity and missed on a given turn, so the former doesn't read as a permanent 100 percent miss rate. This project adds one thing Pi's architecture doesn't need, a host-computed cache-boundary hint passed to provider extensions, because this project has a per-turn `context-transform` chain sitting between the log and the provider call that could silently break a cache prefix in a way nothing in Pi's own architecture can, since Pi has no equivalent extension point there.

## From Pi: the testing discipline

Nearly everything in `docs/testing-plan.md`'s methodology is adapted from Pi's own test suite, which is genuinely large and disciplined for a project in this space. Specifically: the faux provider at `providers/faux.ts` in Pi's `ai` package is the direct model for `lca-testkit`'s fake provider, a scripted, deterministic stand-in that lets the real agent-loop code run in tests with no network access and no cost. Pi's `test/suite/` convention, its own stated rule to use the shared harness, never real provider credentials, and to keep tests CI-safe and deterministic, is adopted as this project's own harness convention almost verbatim. Pi's `test/suite/regressions/` directory, naming each regression test file after the GitHub issue it closes, is the direct precedent for `tests/regressions/` here. Pi's `test.sh`, which sandboxes `HOME`, isolates the package cache, strips environment variables, and disables `GIT_ASKPASS` before running anything, is the model for this project's own test-environment sandboxing fixture. Study all four directly; none of the mechanism changed in the port to Rust, only the language it's implemented in.

## From Pi: the extension examples as evidence of breadth

Pi ships more than thirty example extensions under `examples/extensions/`, and several validated specific design decisions in this document set rather than serving only as general inspiration. `box-pi`, which intercepts tool calls and redirects their execution to a remote sandbox, is real evidence that a hooks world with a replace action, not just allow or deny, does meaningful work; study it when implementing the `hooks` world's pre-tool-use replace path. A pure observability extension forwarding every lifecycle event to an external system is the minimal validation that a hooks-only extension, implementing no other world, is a legitimate and useful shape. `pi-ketch`, wrapping an external, separately-installed CLI tool as a set of agent tools with no daemon and no persistent state, is the direct model for how a `tool`-world extension should use the `process` capability alone, not `net`, when the actual networking happens inside an independently-trusted external binary rather than the extension's own sandboxed code; study it when writing the extension-authoring guide's external-tool-wrapping guidance.

## From Pi: cross-platform rigor

Pi's dedicated Windows test files, `bash-close-hang-windows.test.ts` and `taskkill-enoent.test.ts` among them, its `powershell.ts` tool, its `docs/windows.md`, and its CI pipeline building real `windows-x64` and `windows-arm64` binaries on an actual Windows runner, are the direct reason `docs/platform-notes.md` treats Windows as a first-class target with its own dedicated section rather than an afterthought, and the reason NFR-10 and NFR-12 commit to real Windows CI from Phase 1 rather than deferring it. This is also the most direct contrast with fx, covered below, which has none of this.

## From fx: the native binary and the WASM embedding target

fx's Zig toolchain gives it clean cross-compilation to Linux, macOS, and, less completely, other targets from a single host. fx also builds its agent kernel for `wasm32`: `build.zig` compiles `src/wasm_core_main.zig` and `src/wasm_term_main.zig` into `fx-core.wasm` and `fx-term.wasm`, and the `libfx` JavaScript SDK loads the native addon on Node with a WebAssembly fallback, and WebAssembly with JSPI in browsers (`sdk/README.md`). That is working proof that a real agent compiles to `wasm32` and runs in a JavaScript host, which is evidence this project's web target leans on, not lineage: the native-plus-WASM build shape is this project's own design, specified in FR-WEB-1 through FR-WEB-3 and ADR-0018, and this project's web-hosting mechanism, sibling instantiation through `jco`, is its own answer to a question fx never had to solve, since fx embeds rather than hosts extensions. Study `wasm_core_main.zig` and `wasm_term_main.zig` for what an embedding boundary has to expose. See ADR-0018 for why.

One layer removed from fx: this project uses Rust rather than Zig, and still ended up using Zig anyway, as `cargo-zigbuild`'s linker backend for cross-compiling to macOS and Linux from a single CI runner, pinned alongside `cargo-xwin` per `docs/phase-log.md`. Same linker toolchain, different route to it — fx drives Zig from `build.zig`, this project drives it from Cargo. The dependencies table in the requirements and design document notes this without further comment.

## From fx: the hooks taxonomy

fx's own internal hook system names four lifecycle points — `pre_tool_use`, `stop`, `post_turn_end`, and `attention_required` — in `src/core/hooks/definitions.zig`. They are internal: neither fx's README nor its `sdk/` mentions them, and the handlers live in fx's own tree (`src/builtins/hooks.zig` wires the notification integration), not in any user configuration, so there is no third-party hook surface to study.

This project's `hooks` world carries three of those four names — `on_pre_tool_use`, `on_post_turn_end`, `on_attention_required` — beside points of its own, `on_pre_turn`, `on_post_tool_use`, `on_session_close`, and `on_ui_event`, and deliberately no `stop` point, because this project's turn model has no equivalent to hook. The names are this project's own design for this project's turn model; they coincide with fx's where the shapes coincide. What differs is the surface: this project exposes the same shape of hook points as a genuine third-party extension surface, which is the actual gap fx has here.

## fx: a model-backed permission review, and why this project uses a static one

fx reviews risky actions with a model: `src/gateway/openai_codex_permission_reviewer.zig`, `src/gateway/responses_permission_reviewer.zig`, and `src/gateway/xai_grok_permission_reviewer.zig` stream a review through `src/core/permissions/auto_classifier.zig`, which resolves a review model of its own (`review_model`) and acts on what comes back. There is no single `permission_reviewer.zig` in fx; the reviewers are these three, per gateway. It is a more sophisticated posture than Pi's complete absence of a permission system, and it is not where this project's boundary came from — having a real, enforced permission boundary is this project's own conviction, and its mechanism was never in contention: an LLM's judgment call is not reliably unit-testable the way a static capability check is, and this project's whole approach to being buildable by an AI implementer, laid out in `docs/testing-plan.md`, depends on every security-relevant behavior being expressible as a deterministic, scriptable test against the fake provider. So this project uses the static, manifest-declared, host-enforced capability model throughout `docs/capabilities.md`, precisely because it can be tested the way ADR-0017's cache behavior or ADR-0011's rebinding protection are tested: by scripting a case and asserting on the result, not by trusting a second model's judgment about the first model's actions. Read fx's reviewers for what a model-backed review asks about; read `docs/capabilities.md` for this project's answer.

## From fx: bundling a provider's concerns together

fx's `src/core/gateway/provider_set.zig` bundles a provider's streaming, its model catalog, and its permission classification together as one cohesive unit per provider, rather than scattering related concerns across separate registries. This project's `provider` world is the same shape by its own decision: model listing, streaming, authentication, and now `login`/`logout`/`usage` in one bundle, rather than split across worlds the way `tool` and `command` are kept separate from each other.

## What was deliberately not taken from fx

fx keeps skills handling, MCP support, and subagent orchestration as built-in, core features with no third-party extension point. This project made a different choice for skills specifically: it's a first-party extension, native-linked by default, but built against the same public ABI a third party would use, per ADR-0013, because everything skills-handling needs turned out to be expressible through existing worlds. This project also doesn't build subagent orchestration into 1.0 at all, core or extension; nothing in this document set currently specifies it, and it's a candidate for a future extension world once a real need surfaces, following the same evidence-based growth discipline the capability catalog already uses.

fx's total absence of Windows support and its "experimental, use at your own risk" status are cautionary reference points, not inspiration. They're named here so a future contributor understands why `docs/platform-notes.md` treats Windows with the weight it does: not because Windows is intrinsically harder, but because fx's own gap there is direct evidence of what happens when it isn't treated as first-class from the start.

fx's total absence of a general-purpose, third-party extension API, only Skills, MCP, and Subagents as fixed, sanctioned surfaces with no sandboxing, no capability model, and no consent screen, is the gap this whole project exists to fill for the native-binary architecture fx otherwise validates. Nothing about fx's own extension story was available to port, because fx doesn't have one in the sense this project needs.

## What belongs to neither project

Several load-bearing pieces of this design have no direct precedent in either codebase and were worked out from scratch, for a contributor's own orientation about where the genuinely new engineering risk in this project actually sits, as opposed to the parts that are a well-trodden port of an existing, working design.

The WIT-typed, Component Model extension ABI itself: Pi's extensions are plain TypeScript with no formal interface description, and fx has no general extension ABI to compare against at all. The capability-gated import-table enforcement model, where an extension's access is determined by what's in its import table rather than by a runtime permission check the extension's own code could choose to skip, has no equivalent in either project, since Pi enforces nothing and fx's enforcement is a runtime judgment call rather than a static grant. The widget-tree UI rendering model that prevents an extension from ever writing raw terminal escape sequences, specified in ADR-0003, is a direct reaction against Pi's own liberal model, where an extension can, in the plainest possible terms, do whatever it wants to the terminal; nothing in fx's design was available to draw on here either, since fx has no third-party UI-rendering extensions to compare against. The dual native-linked-and-WASM delivery mode from a single extension source tree, specified in ADR-0002 and ADR-0013, exists in neither project, since neither compiles the same extension source two different ways. `net-local` and its DNS-rebinding protection, the OCI-and-HTTPS-archive distribution model, and the cache-boundary hint mechanism specifically, as opposed to the cache-waste measurement it supports, are all new work motivated by risks or opportunities unique to this project's own architecture.

## Guidance for working from the source directly

When a design question comes up that this document set doesn't already answer, and the two source trees are available to check, the working order is: look for how Pi handles the equivalent case first, since Pi's design is the closer match to this project's own scope and philosophy in almost every dimension except the sandbox; check whether fx does anything relevant only if the question is specifically about the native-binary or WASM-embedding side of things, where fx is the more directly comparable project; and if neither has an answer, that's a signal the question is in the genuinely novel third of this design, not a signal to guess, and it belongs as a new ADR following the same format as the forty-two already written, not as an undocumented judgment call made once and never revisited.
